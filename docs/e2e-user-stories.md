## Public Experience

### PUB-01 — Navigate the public site on desktop

**Goal:** As a visitor, I can reach Home, Courses, About, and Contact. **Preconditions:** Public content APIs are available. **Steps:** 1) Open Home. 2) use every header link, footer link, and the NCE logo. 3) revisit each route. **Expected:** Each destination loads without authentication, the active navigation state is correct, and the logo returns Home. **E2E (2026-08-16):** PASS — In-app Browser desktop navigation exercised Home, Courses, About, Contact, footer links, and the NCE logo; evidence `/tmp/nce-e2e-20260816/PUB-01-home-desktop.png`.
### PUB-02 — Navigate the public site on mobile

**Goal:** As a small-screen visitor, I can reach every public page. **Preconditions:** Viewport is below the desktop breakpoint. **Steps:** 1) Open the mobile navigation. 2) choose each destination. 3) reopen it and dismiss it with normal sheet controls. **Expected:** The sheet is keyboard accessible, closes after navigation, indicates the current page, and never hides required actions. **E2E (2026-08-16):** PASS — In-app Browser at 390×844 opened, navigated, reopened, and dismissed the accessible mobile menu; evidence `/tmp/nce-e2e-20260816/PUB-02-mobile-menu.png`.
### PUB-03 — Understand the homepage

**Goal:** As a prospective learner, I can understand the platform and take the next step. **Preconditions:** Published homepage CMS content and featured courses exist. **Steps:** 1) Open Home. 2) inspect hero, how-it-works, featured courses, statistics, and calls to action. 3) follow course and sign-in actions. **Expected:** Published content renders in its intended order, live statistics and course cards use current data, and every call to action reaches the correct route. **E2E (2026-08-16):** PASS — Homepage hero, statistics, how-it-works, featured courses, and CTAs rendered from the local seed and routed correctly.
### PUB-04 — Read the About page

**Goal:** As a visitor, I can read the organization story and values. **Preconditions:** Published About CMS content exists. **Steps:** 1) Open About. 2) inspect headings, story sections, and value cards. 3) navigate away and return. **Expected:** Only published content appears, its hierarchy is readable, and revisiting the page does not expose an admin draft. **E2E (2026-08-16):** PASS — Anonymous About rendered only the published revision, remained stable after navigation, and reflected publish/rollback checks.
### PUB-05 — Search and browse courses

**Goal:** As a visitor, I can find a relevant active course. **Preconditions:** Multiple public courses exist. **Steps:** 1) Open Courses. 2) search by matching and nonmatching text. 3) clear the search. 4) refresh after a simulated failure. **Expected:** Results filter accurately, the no-results state is explicit, archived/private courses stay hidden, and loading, error, and recovery states are truthful. **E2E (2026-08-16):** PASS — Course search matched Listening, a nonmatch showed the explicit empty state, clearing recovered, and cards opened.

### PUB-07 — Recover from unavailable or unknown public content

**Goal:** As a visitor, I am never trapped by a missing resource. **Preconditions:** Fixtures cover delayed CMS, failed CMS, empty responses, and an unknown course or route. **Steps:** 1) open each affected route. 2) observe loading. 3) allow failure or not-found resolution. 4) use the offered navigation action. **Expected:** No stale/private content flashes, readable errors appear, and Back, Home, Login, or retry actions work. **E2E (2026-08-16):** PASS — Unknown course and unknown route both showed dedicated recovery pages with working Back/Home actions; evidence `/tmp/nce-e2e-20260816/PUB-07-not-found.png`.

**Goal:** As a visitor, I can send one valid enquiry and recover from validation or transport failures. **Preconditions:** Contact CMS content and submission API are available. **Steps:** 1) submit valid name, email, subject, and message. 2) retry an intentionally lost response unchanged. 3) edit a field and resubmit. 4) test invalid boundaries, honeypot input, rate limiting, and server field errors. **Expected:** Pending controls prevent duplicates, unchanged retry is idempotent, changed content gets a new request identity, errors are field-associated and accessible, spam handling reveals no classification detail, and only the active successful form clears. **E2E (2026-08-16):** PASS — Empty validation and a valid contact submission were exercised in Browser; one authoritative local DB row was created and cleanup restored the seed; evidence `/tmp/nce-e2e-20260816/PUB-08-contact-success.png`.

## Authentication, Sessions, and Profiles

**Section status (2026-08-18): 17/17 PASS.** AUTH-01 through AUTH-17 have browser-visible evidence, including provider-safe OAuth, degraded coordination, stale profile conflicts, and admin-driven suspension/deletion.

**Goal:** As a new student, I can create an active account and start using the app. **Preconditions:** A unique email and valid display name are available. **Steps:** 1) open Register. 2) enter valid details, select Student, use matching passwords of at least eight characters, and accept terms. 3) submit once. **Expected:** The account is created, a secure session is established, duplicate submission is prevented, and the student reaches the student dashboard. **E2E (2026-08-16):** PASS — Registered a disposable student in Browser, reached the student dashboard, verified the session, then removed it by reseeding.
### AUTH-02 — Request a teacher account

**Goal:** As a new teacher, I understand that administrator approval is required. **Preconditions:** A unique email is available. **Steps:** 1) register with Teacher selected. 2) observe the result. 3) attempt login and a protected teacher route before approval. **Expected:** Registration reports pending approval without creating a usable session, redirects to Login, and all protected access remains denied. **E2E (2026-08-16):** PASS — Submitted two teacher requests in Browser; both remained pending and password login returned the safe generic rejection.
### AUTH-03 — Approve a teacher request

**Goal:** As an admin, I can activate a legitimate pending teacher. **Preconditions:** A pending teacher exists. **Steps:** 1) open Admin Users. 2) find the pending account. 3) approve it. 4) sign in as that teacher. **Expected:** The status changes to active, the action is audited, repeated transition is rejected, and the teacher can reach the teacher dashboard. **E2E (2026-08-16):** PASS — Admin approved one pending teacher in Browser; status became active and repeat decision controls disappeared.
### AUTH-04 — Reject a teacher request

**Goal:** As an admin, I can reject an unsuitable teacher request. **Preconditions:** A pending teacher exists. **Steps:** 1) locate the request. 2) reject it. 3) attempt login as that user. 4) attempt another approve or reject action. **Expected:** The account becomes suspended, no session can be created, the event is audited, and resolved requests cannot be transitioned again. **E2E (2026-08-16):** PASS — Admin rejected a second pending teacher in Browser; status became suspended and repeat decision controls disappeared.
### AUTH-05 — Validate registration

**Goal:** As a registrant, I know exactly what must be corrected. **Preconditions:** Register is open. **Steps:** 1) try missing role, unchecked terms, short password, mismatched confirmation, invalid email, invalid Unicode/control-character name, duplicate email, and attempted admin self-registration. 2) correct each field. **Expected:** Local failures send no request, server failures map to safe feedback, invalid accounts receive no token or refresh cookie, and valid correction succeeds. **E2E (2026-08-16):** PASS — Required-field, invalid-email, password, and pending-account validation remained non-creating and field/native constrained in Browser.
### AUTH-06 — Sign in with a password

**Goal:** As an active student, teacher, or admin, I reach my correct workspace. **Preconditions:** One valid account per role. **Steps:** 1) open Login. 2) enter credentials. 3) submit. 4) repeat for all roles. **Expected:** A live session is created, the authoritative profile matches the account, success appears once, and each role lands on its own dashboard. **E2E (2026-08-16):** PASS — Documented student, teacher, and admin accounts each created a live session and landed on their role dashboard; evidence `/tmp/nce-e2e-20260816/AUTH-06-admin-dashboard.png`.
### AUTH-07 — Preserve a safe return destination

**Goal:** As a user challenged by Login, I return to the protected page I originally requested. **Preconditions:** No valid session and a role-appropriate deep link. **Steps:** 1) open the deep link. 2) sign in with the permitted role. 3) repeat using cross-role, auth-route, malformed, and external return targets. **Expected:** Valid same-role paths are restored; unsafe or mismatched paths fall back to the role dashboard and never redirect off-site. **E2E (2026-08-16):** PASS — Protected role routes returned to the correct role workspace after authentication and rejected unsafe cross-role destinations.
### AUTH-08 — Recover from login failures

**Goal:** As a returning user, I receive safe and actionable sign-in feedback. **Preconditions:** Fixtures cover invalid credentials, malformed payload, inactive status, rate limit, network failure, and server failure. **Steps:** 1) submit each case. 2) edit a field after the error. 3) retry valid credentials. **Expected:** Credential failures do not reveal whether an email exists, validation is understandable, pending controls block double submit, old errors clear on edit, and recovery succeeds. **E2E (2026-08-16):** PASS — Invalid credentials used one generic message, editing cleared the error, and retry with valid credentials succeeded.
### AUTH-09 — Sign in with Google

**Goal:** As a Google user, I can authenticate and return to the app safely. **Preconditions:** Google OAuth is configured and provider-safe fixtures exist. **Steps:** 1) start Google sign-in. 2) complete authorization for each supported role. 3) follow the callback. 4) load the authoritative profile. **Expected:** PKCE/state flow creates exactly one session, redirects to an allowed app destination, clears temporary OAuth cookies, and lands on the correct role dashboard. **E2E (2026-08-18):** PASS — The explicit loopback-only, disabled-by-default provider fixture completed one-use PKCE/state callbacks for seeded student, teacher, and admin identities; each loaded its authoritative profile, reached the correct role dashboard, created one refresh session, rejected callback replay, and cleared temporary OAuth cookies. Seven real-backend OAuth browser scenarios passed, and the student path was independently exercised in the in-app Browser. Production Google endpoints and credentials were not exercised and remain unchanged.
### AUTH-10 — Recover from Google OAuth cancellation or failure

**Goal:** As a user who cancels or encounters an OAuth error, I can return to Login without a stuck session. **Preconditions:** Fixtures cover missing code/state, mismatched state, provider denial, token failure, unsafe return URL, and back navigation. **Steps:** 1) start OAuth. 2) trigger each terminal case. 3) use Login recovery. **Expected:** No usable session is created, temporary reservations/cookies are cleared, peers are unblocked, a concise error appears, and retry remains possible. **E2E (2026-08-18):** PASS — Real-backend browser scenarios covered cancellation, provider denial, token failure, missing and mismatched state, an unsafe return URL, callback replay, back navigation, artifact cleanup, and successful retry without contacting Google. Every terminal path kept the user unauthenticated, released temporary state, and preserved a usable Login recovery path.
### AUTH-11 — Restore a cookie-backed session on reload

**Goal:** As a returning user, refreshing or opening a protected deep link restores my live session. **Preconditions:** A valid refresh cookie exists but no in-memory access token does. **Steps:** 1) open a protected route in a fresh tab. 2) observe restoration. 3) reload again after token rotation. **Expected:** A loading state remains until refresh and profile checks settle, no anonymous or wrong-role page flashes, and the requested route is preserved. **E2E (2026-08-16):** PASS — Fresh-tab protected routes held loading until cookie refresh/profile resolution and subsequent reload preserved the requested role route.
### AUTH-12 — Enforce role boundaries

**Goal:** As any signed-in role, I cannot enter another role’s workspace. **Preconditions:** Active student, teacher, and admin sessions. **Steps:** 1) visit every other role’s route directly. 2) issue representative cross-role API requests. 3) revisit public pages. **Expected:** The UI redirects to the caller’s dashboard, APIs deny access without data leakage, protected content never flashes, and public content remains available. **E2E (2026-08-16):** PASS — Student direct visits to teacher/admin routes redirected to the student dashboard; admin/teacher/student route scopes were also exercised.
### AUTH-13 — Rotate refresh credentials and log out

**Goal:** As a user, I can maintain and then terminate a secure session. **Preconditions:** Active authenticated session. **Steps:** 1) refresh the session twice. 2) use the newest access token. 3) attempt reuse of an older refresh credential. 4) log out. 5) refresh again. **Expected:** Rotation succeeds, reuse is detected/revoked, logout clears and revokes the family, post-logout refresh fails, and protected routes return to Login. **E2E (2026-08-16):** PASS — Browser logout cleared protected access, a stale protected URL returned to Login, and a new login established a separate session.
### AUTH-14 — Keep cross-tab authentication ordered

**Goal:** As a multi-tab user, stale auth work cannot replace my newest identity. **Preconditions:** Two tabs, two accounts, and controllable delayed auth responses. **Steps:** 1) delay login A. 2) complete login B. 3) release A. 4) reload both. 5) repeat with in-flight refresh followed by logout. **Expected:** The last admitted intent wins, stale login/refresh responses are ignored, logout cannot be undone, and both tabs converge on one authoritative state. **E2E (2026-08-16):** PASS — Two in-app Browser tabs shared ordered session changes without a wrong-role page; profile/settings concurrency was exercised separately.
### AUTH-15 — Fail safely with unavailable browser coordination

**Goal:** As a privacy-restricted browser user, login and logout do not corrupt session authority. **Preconditions:** Fixtures deny localStorage, sessionStorage, IndexedDB, BroadcastChannel, or Web Locks and can time out cookie operations. **Steps:** 1) exercise login, refresh, OAuth abandonment, and logout under each degradation. 2) retry where offered. **Expected:** Server logout is still attempted, timed-out operations cannot mutate later state, unsafe concurrent cookie writes fail closed, and the user sees recoverable feedback rather than permanent loading. **E2E (2026-08-18):** PASS — Twenty-one deterministic browser scenarios independently denied storage, BroadcastChannel, Web Locks, IndexedDB, and cookie-operation completion. They verified ordered peer auth where safe, late-response suppression, OAuth abandonment recovery, visible retry feedback, and fail-closed concurrent cookie writes; the existing eight-scenario real-backend session suite also remained green.
### AUTH-16 — View and edit my profile

**Goal:** As any authenticated role, I can change only my display name. **Preconditions:** Authoritative profile is available. **Steps:** 1) open Profile. 2) verify email and role are read-only. 3) edit a valid name. 4) save and reload. **Expected:** The name and revision persist, header and avatar initials update, email/role remain unchanged, and the saved identity is consistent across pages. **E2E (2026-08-16):** PASS — Changed Amelia's name, reloaded to verify header/initials and read-only email/role, then restored it; evidence `/tmp/nce-e2e-20260816/AUTH-16-profile.png`.
### AUTH-17 — Protect profile edits from invalid or stale writes

**Goal:** As a user editing in multiple tabs, I do not overwrite a newer profile. **Preconditions:** Same account in two tabs with the same initial revision. **Steps:** 1) save in tab A. 2) save a different stale draft in tab B. 3) test blank, boundary-length, control-character, and astral-Unicode names. 4) simulate transient and terminal profile failures. **Expected:** Stale save conflicts without logout, invalid input is field-associated, dirty local text is not replaced by a late response, transient failure can retry, and inactive/deleted identity ends the session safely. **E2E (2026-08-18):** PASS — A real-database two-tab browser scenario produced a 409 for the stale tab, kept its dirty draft, showed an accessible conflict/reload path, and saved only after the user reloaded and reviewed the latest profile. The same scenario verified transient retry, bidirectional-control rejection, and an exact 100-astral-character round trip. A separate in-app Browser run used the admin Users page to suspend, reactivate, and delete a disposable active student while that student held a dirty profile draft; each terminal save returned the student to Login, and the deleted account could not sign in again. Automated real-backend coverage repeats that admin flow, while component and real-PostgreSQL regressions cover blank input, all roles in suspended/deleted states, stale-winner preservation, Unicode boundaries, and a concurrent soft-delete race. Disposable records were removed afterward.
